# Changelog

All notable changes to HalalForMe are recorded here, newest first. Format: date, area, what changed, why it mattered. See [CLAUDE.md](./CLAUDE.md) for the rule that this file is updated in the same change as the feature itself, never after the fact.

## 2026-07-15 (4)

### Reliability
- **Edge function error logging and silent-failure fixes.** `weekly-digest/index.ts` now checks the return value of the `admin_notifications` DB insert — if it fails, the function returns HTTP 500 with the error detail instead of 200 silently (cron invocations that fail were previously completely invisible). Also checks `pushRes.ok` on the Expo push API call and logs non-200 responses. `notify-admin/index.ts` gets the same treatment: DB insert error now returns 500, and Expo push API HTTP failures are logged. Client call sites in `app/submit-restaurant.tsx` and `app/claim-restaurant/[id].tsx` had bare `.catch(() => {})` — changed to `.catch(err => console.warn('notify-admin failed:', err))` so failures surface in device logs without blocking the user flow.

## 2026-07-15 (3)

### Observability
- **Added Sentry crash and error monitoring.** `@sentry/react-native` initialized in `app/_layout.tsx` before any component renders; root layout wrapped with `Sentry.wrap()` to install a React error boundary and native crash handler over the full app tree. `enabled` is gated on `EXPO_PUBLIC_SENTRY_DSN` so the SDK is a no-op in dev builds without a DSN configured. Auth boot failures (previously silently swallowed in `AuthContext`) now captured with `{ tags: { context: 'auth_boot' } }`. Push token registration failures now captured instead of swallowed. Sentry user context (`Sentry.setUser`) is kept in sync with the session so every error report is tagged with the user's ID. The `@sentry/react-native/expo` build plugin is wired into `app.json` for source map upload on EAS builds (fill in `YOUR_SENTRY_ORG` / `YOUR_SENTRY_PROJECT` before first production build).

## 2026-07-15 (2)

### Performance
- **Added missing indexes on core tables (`031_indexes.sql`).** Nine indexes across five tables that were causing full table scans on the most common query patterns: `reviews(restaurant_id)` (restaurant detail page), `reviews(status, created_at DESC)` (admin moderation queue, replaces sort after scan), `submissions(user_id)` and `submissions(status, created_at DESC)` (user submissions screen + admin dashboard), `restaurant_claims(user_id)` and `restaurant_claims(status, created_at DESC)` (user notifications + admin claims — the existing UNIQUE constraint has `restaurant_id` as the left column so `user_id`-only queries couldn't use it), `admin_notifications(created_at DESC)` and a partial index on `admin_notifications WHERE is_read = false` (dashboard unread count + mark-all-read), and `restaurants(lat, lng)` (bounding-box geo range queries in the home and search screens had no index at all).

## 2026-07-15

### Security
- **Row-Level Security enabled on all previously-untracked core tables (`029_rls_core_tables.sql`).** Eight tables created before migration tracking started (`profiles`, `restaurants`, `reviews`, `saved_restaurants`, `submissions`, `restaurant_claims`, `push_tokens`, `admin_notifications`) had no RLS or policy definitions in any tracked migration — multi-user data isolation relied entirely on application-level `.eq('user_id', ...)` filtering with no database backstop. Migration `029` enables RLS on all eight and creates named, idempotent policies following the same `DROP POLICY IF EXISTS` + `CREATE POLICY` pattern established in `015_scan_reports.sql`. Access model: public read for discovery content (restaurants, reviews, profiles); owner-only for private data (saved lists, device tokens); admin-only for internal operations (admin notifications). Edge functions continue to use the service-role key and are unaffected by these policies.
- **Dropped insecure pre-existing `push_tokens` policy (`030_baseline_schema.sql`).** A `"Service role reads all"` policy on `push_tokens` applied `TO public` with `USING (true)`, meaning any unauthenticated caller with the anon key could `SELECT * FROM push_tokens` and read every user's device push token. Dropped in migration `030` via `DROP POLICY IF EXISTS`.

### Schema
- **Baseline `CREATE TABLE` migration captured for all eight previously-untracked tables (`030_baseline_schema.sql`).** Schema verified against the live database via `information_schema` introspection on 2026-07-15. The full schema is now reproducible from `supabase/migrations/` alone. Notable correction: `restaurants.avg_rating` and `restaurants.review_count` **do exist** as nullable live columns — a prior note in `DATABASE_SCHEMA.md` incorrectly said they did not.

## 2026-07-14 (2)

### Added
- **New Tier 1b: Masjidal.com widget API.** Masjidal (mymasjidal.com / masjidal.ca) sells "Adhan Clock" prayer-time display hardware; mosques that use it manage their schedule in Masjidal's own portal and embed a read-only widget (`masjidal.com/widget/monthly/?masjid_id=...`) on their site via iframe. That widget's own JS (`monthlyScript.js`) calls a public, unauthenticated JSON endpoint — `masjidal.com/api/v1/time/range?masjid_id=...` — returning structured adhan, iqama, and both jummah session times directly, no HTML rendering or scraping involved. `findMasjidalId()` looks for a `masjid_id` query param on either the mosque's own URL or any iframe discovered by the fix above (a mosque can enter the Masjidal widget URL directly as "their website," or embed it on their own site), and `tryMasjidal()` calls the API directly when found. Verified against the live API with a real `masjid_id` before shipping.
- **New Tier 1c: embedded Google Sheets "publish to web" CSV schedules.** Deployed the iframe/Masjidal fixes above and confirmed via Supabase function logs that ISCN's own widget iframe was now being discovered and fetched correctly, but the iqama/jummah times were still coming up empty — because the widget's table is built entirely by client-side JS, so even Jina.ai's renderer (Tier 5) was needed, and Jina's anonymous tier is returning `403` from Supabase's Edge Function IP (confirmed live in logs, not just locally). Rather than depending on Jina working, `findGoogleSheetCsvUrl()`/`tryGoogleSheetSchedule()` pull the mosque's actual source-of-truth directly: many of these widgets (including ISCN's) fetch their iqama data from a Google Sheet published as CSV, and that publish URL is plainly visible in the widget's own JS. `parseScheduleCsv()` matches prayer columns generically by header keyword (`fajr`/`zuhr`/`dhuhr`/`asr`/`maghrib`/`isha`, plus a `jum`-matching column for jummah) rather than assuming fixed column positions, and picks the most recent "effective as of today" row rather than assuming one row per calendar day — real sheets turned out to have blank separator rows and sparse date-range entries, not a clean daily table. Every field fails closed to `null` on anything that doesn't parse as a clock time (e.g. ISCN's own sheet stores Maghrib as a relative `" +7 mins"` offset from adhan, not a time, since that mosque computes it rather than storing it — left blank rather than guessed) — verified against the real live CSV across three different dates in the year, including checking the "effective from" row-selection logic didn't drift into a future or stale entry.

### Fixed
- **New iframe-following code (added earlier the same day, see below) could extract wrong iqama/jummah times instead of none.** The new direct-HTML-text extraction pass ran `extractIqamaFromText`/`extractJummahFromText` against `stripHtml()`'d iframe content, but `stripHtml()` only removed HTML tags, not `<script>` contents — so a mosque widget's embedded JS (e.g. a hardcoded fallback schedule array with `fajr:'6:15 am', ..., jumuah:'...1:30 pm'` all on one line) got misread as page text, with the "prayer name keyword → last time on the line" heuristic grabbing an unrelated value (reproduced: returned `fajr: "1:30 PM"`, actually the jumuah time from an unrelated row). Worse, because this counted as "found," it silently skipped the Jina-rendering fallback tier that would have gotten the real value. `stripHtml()` now drops `<script>`/`<style>` block contents entirely before tag-stripping, not just their tags — verified against the real file that this now correctly returns no match, falling through to Jina as intended.

## 2026-07-14

### Fixed
- **`parse-mosque-website` couldn't see iqama times published as an embedded iframe widget.** Investigated using coronamuslims.com/ISCN as a concrete example: its monthly prayer-times table isn't in the page's own HTML at all — it's an `<iframe loading="lazy" src=".../iscn-prayer-times-v2.html">` pointing at a separately-uploaded static file, which itself computes adhan times client-side and fetches iqama times from a published Google Sheet CSV via `fetch()` at runtime. None of the 5 existing tiers ever requested that URL, so a real, well-structured mosque schedule silently produced nothing. `supabase/functions/parse-mosque-website/index.ts` now (1) discovers `<iframe>` src URLs in the fetched page (`findIframeUrls`, filtered against a blocklist of known non-content embeds like YouTube/Maps/social widgets) and fetches each one, (2) reuses that content across the existing JSON-LD and Google Calendar tiers, and as a new cheap pre-Jina pass runs the iqama/jummah text heuristics directly against it, and (3) additionally points the Jina.ai renderer at each iframe URL (not just the top-level page) so client-JS-rendered widget content gets rendered too.
- **Iqama-table text heuristic (`extractIqamaFromText`) only understood one table orientation.** It assumed a single "Iqama" column with the prayer name in the next column over (one row per prayer) — the opposite shape from a common "monthly calendar" layout (one row per *date*, with a separate `Iqama` column repeated after each prayer's adhan column, e.g. `Fajr | Iqama | Dhuhr | Iqama | Asr | Iqama`). Added `extractCalendarIqama()` as a new first-pass strategy: it pairs each `Iqama` header with the nearest preceding prayer-name header, then picks the calendar row closest to today's date (parsing common date formats — `"Jul 01"`, `M/D`, `M/D/YYYY`, `YYYY-MM-DD` — via `parseLooseDate()`).

## 2026-07-11 (4)

### Fixed
- **Security (High) — `notify-user`/`notify-admin` Edge Functions had no caller authentication.** Both ran with the service-role key and only validated that required body fields were present — nothing checked *who* was calling. `notify-user` (`supabase/functions/notify-user/index.ts`) would push an arbitrary title/body to any user by UUID; `notify-admin` (`supabase/functions/notify-admin/index.ts`) would insert arbitrary rows into `admin_notifications` and push every admin. Every real call site of `notify-user` is an admin action (claim/submission/review approve-or-reject — see `app/(admin)/claim/[id].tsx`, `app/(admin)/review/[id].tsx`, `app/(admin)/reviews.tsx`), so it now requires a signed-in caller with `profiles.is_admin = true` (verified server-side via the caller's own JWT, not trusted from the request body). Every real call site of `notify-admin` is a regular signed-in user completing an already account-gated action (`app/submit-restaurant.tsx`, `app/claim-restaurant/[id].tsx`), so it now just requires a valid session. `supabase.functions.invoke()` already sends the caller's session JWT by default, so no client-side call sites needed changes.
- **Security (High) — verified, not a bug:** the audit also flagged that RLS on the untracked `restaurants`/`restaurant_claims` tables couldn't be confirmed from the repo. Checked live via `pg_policies` (2026-07-11): `restaurant_claims` UPDATE is gated to `profiles.is_admin`, `restaurants` UPDATE is gated to admins or the original submitter while `is_verified = false` — non-admins cannot approve their own claim or edit a published listing directly against the DB, matching the client-side route guards. No owner-edit-after-claim screen exists yet for restaurants (unlike mosques), so there's no gap there either — just unused surface.

## 2026-07-11 (3)

### Fixed
- **Security (Critical) — mosque invite codes were publicly readable.** The `"Public read access on mosques"` RLS policy from `017_mosques.sql` was `USING (true)` with no column restriction — RLS is row-level only, so it exposed `invite_code` to anyone with the public anon key, not just the legitimately-public fields (name, address, iqama times, etc.). A single query against the live table could dump every unclaimed mosque's invite code and claim ownership via `redeem_mosque_invite()` without ever being handed a code by an admin — defeating the entire out-of-band invite model described in that migration's own comments. Fixed in `022_mosque_invite_code_lockdown.sql` with a column-level `REVOKE SELECT (invite_code) ON mosques FROM anon, authenticated` rather than restructuring the table — the row-level policy for every other field was already correct and intentional. Admins now read a mosque's code through a new `get_mosque_invite_code()` `SECURITY DEFINER` RPC (checks `is_admin` itself, same pattern as `redeem_mosque_invite`) instead of a direct column select; `app/mosque/[id]/index.tsx` updated accordingly (`createPage()` no longer reads the code back from the DB at all — it already has the value it just generated locally).
- **Hardening, found by the same audit:** `generateInviteCode()` (`lib/mosques/manual.ts`) generated codes with `Math.random()`, not a CSPRNG — switched to `expo-crypto`'s `getRandomBytes` (already a dependency, already used for `generateManualOsmId`). Five `SECURITY DEFINER` trigger functions from `009_gamification.sql`/`011_review_points.sql` (`check_and_award_badges`, `award_submission_points`, `award_photo_points`, `award_review_points`, `approve_review_photos`) didn't pin `search_path`, unlike `redeem_mosque_invite`/`delete_user` which already did — all five now do.
- **Not yet addressed, needs action outside this repo:** a full security audit also flagged that admin-only writes to untracked tables (`restaurants`, `restaurant_claims`, `submissions`, `reviews`) can't be verified from this repo — their live RLS needs checking directly against Supabase to confirm non-admins can't call the same updates directly; the `notify-user`/`notify-admin` Edge Functions don't authenticate their caller; and the `halal_certificates` storage bucket's public/private setting and per-user path scoping need confirming in the Supabase dashboard.

## 2026-07-11 (2)

### Fixed
- **Explore hub search felt frozen for every query, not just mosque names.** `handleSearch()` (`app/(tabs)/search.tsx`) always awaited a full mosque-name check before deciding where to navigate — even for an obvious restaurant search like "Kabob House" — and that check ran a live Overpass (OpenStreetMap) query with no visual feedback at all (a `searching` state was set but never wired into the UI). Public Overpass mirrors are hedged across up to several instances with a 6s per-mirror timeout, so a slow/rate-limited primary could make any search wait multiple seconds looking unresponsive.
  - The mosque check is now staged: the fast local `mosques` table (`searchMosquesByName`) is checked first, and OpenStreetMap (`searchOsmMosquesByName`) is only consulted if that comes back empty — capped at 2.5s via `Promise.race`, falling through to food search immediately if OSM hasn't answered by then instead of waiting out the full hedge chain.
  - The search bar now shows a spinner in place of the search icon and disables the input while `searching` is true, so even the capped wait has visible feedback instead of looking frozen.

## 2026-07-11

### Fixed
- **Push token registration gap closed (backfilled entry — undocumented at the time).** `registerPushToken()` (`lib/notifications.ts`) was only called from the in-app Notifications screen (`app/notifications.tsx`), so `push_tokens` had no row for a signed-in user until they happened to visit that screen — most users were unreachable by server-side push even though the sending logic (Edge Functions, submission/claim/review call sites) was fully correct. `app/_layout.tsx` now also calls `registerPushToken()` from a `useEffect` keyed on `session?.user?.id`, firing on every sign-in so every signed-in device registers a token automatically, not only those who've visited the Notifications screen. This was the single highest-leverage item in Phase 6 (see `docs/phase6.md`). ## 2026-07-10

### Added
- **Follow a mosque for Iqama times.** A user can now follow one mosque (`app/mosque/[id]/index.tsx`, "Follow for Iqama Times" button) to see its posted Iqama time alongside the computed Adhan time on Home — in the hero card's next-prayer footer and in the "All Prayers" sheet, plus a "Followed Mosque" row in Settings to see/clear it. Deliberately additive, never a replacement: the Adhan countdown and notification schedule stay driven entirely by the existing astronomical calculation (`lib/prayer/calculate.ts`), since a mosque's Iqama time is owner-entered and can go stale in a way the computed time never can — if the followed mosque's data is missing or the fetch fails, the annotation just doesn't show, nothing else on Home is affected. Stored as `followedMosqueId` (the `mosques.id` UUID) on the existing local, device-level `PrayerSettings` (`lib/prayer/settingsStore.ts`) — no account sync, no migration, consistent with how method/madhab/precaution-buffer already work.
  - **Fixed same day:** the Iqama annotation didn't appear on Home after tapping "Follow" until the app was fully reloaded. Home's `settings` state is only ever loaded once on mount (the location-resolution effect), so a `followedMosqueId` change written from the mosque page — a different screen — never reached it. The Iqama-fetch effect now re-reads `followedMosqueId` straight from storage on every focus instead of depending on that mount-only state, and "Stop Following" in Home's own Settings sheet updates the displayed mosque immediately (that action doesn't cross a focus boundary, so the focus-based refetch alone wouldn't have caught it).

### Fixed
- **Home's Upcoming Events/Jummah cards showed stale data after editing a mosque page.** Both were saved correctly to the DB, but Home only fetched them once per resolved location (`useEffect` on `[coords]`) — navigating away to the manage screen, editing, and coming back to Home never re-triggered a fetch. Switched to `useFocusEffect` so it refetches every time Home regains focus, not just when location changes.
- **Explore hub category tiles had mismatched background colors.** Each `CATEGORIES` entry in `app/(tabs)/search.tsx` carried its own `bg` (orange for food, green for mosques, teal for grocery/butcher), overriding the single shared tone (`#EDEBE4`) `categoryIconBox` already defaulted to. Removed the per-tile overrides so all tiles use one consistent background, matching the intended design.
- **Mosque contact email saved but never displayed.** `app/mosque/[id]/index.tsx`'s details card had rows for phone and website but none for `contact_email` — the field was fetched, saved correctly by the manage screen, and simply never rendered. Added the missing row (opens a `mailto:` link, same pattern as phone/website).

### Changed
- **Mosque page (including Jummah times) rendered noticeably faster.** `loadData()` awaited two Supabase queries sequentially (the `mosques` row, then `mosque_posts`) before clearing the loading state — so Jummah times, which live entirely on the first query, were held behind the second, unrelated one finishing too. `setLoading(false)` now fires right after the first query resolves; events/announcements populate independently afterward instead of gating the whole screen.

- **"Manage a Mosque" always re-asked for the invite code.** Redeeming a code grants permanent ownership (`mosques.owner_id`), but `app/redeem-mosque.tsx` had no check for that — it showed the code-entry form unconditionally every time, even for someone who'd already redeemed one and just navigated away and back. Now checks (on every screen focus) whether the signed-in user already owns a mosque: zero → same code-entry form as before; exactly one → skips straight to that mosque's manage screen; more than one (a person managing multiple mosques) → a picker instead of only ever jumping to the first.
- **...which then sent existing owners to a "you don't manage this page" error.** The ownership-check fix above navigated using the mosque's OSM id, but `app/mosque/[id]/manage.tsx`'s `[id]` is the `mosques` table UUID, not the OSM id (`.eq('id', mosqueId)`) — so the redirect and the picker both landed on a route that could never match, tripping the unauthorized state for a real owner. Fixed to navigate with `mosques.id` instead.

### Changed
- **Overpass mirror fallback — hedged instead of sequential.** `lib/mosques/overpass.ts` tried its three public Overpass mirrors one at a time with a 15s timeout each, so a slow/rate-limited primary could stall mosque loading for up to 45s worst case. Replaced with a hedged-request pattern (`raceOverpassMirrors()`, shared by both `fetchNearestMosques` and `searchOsmMosquesByName`): the primary fires immediately, the next mirror only fires *in addition* if the primary hasn't answered within 2.5s (or immediately on an outright failure, without waiting out the rest of that delay), and so on — whichever responds first wins. Per-mirror timeout also cut from 15s to 6s. Deliberately not full parallel racing (`Promise.any` on all three at once) — these are public, shared, rate-limited mirrors (per the existing 429 warning in the file), and hedging gets most of the latency win without tripling request volume on every single call.

Removed the filter; `distanceMi` now defaults to `0` for a row missing coordinates instead of the row being dropped entirely.

## 2026-07-05

### Fixed (Phase 1 QA Audit)
A full verification pass across Home, Qibla, Explore, Scanner, and Profile (execution-flow tracing, DB/schema cross-checks against actual tracked migrations, navigation-target verification) found and fixed:
- **Home — midnight-to-Fajr display bug.** Between midnight and Fajr, the hero card showed a stuck "Resolving prayer times…" even though `times` and the next prayer (Fajr) were fully resolved, because the current-prayer lookup only considered prayers already past for the day. Added a "Next" state to the hero card for exactly this window.

- **Explore — rating filter silently broken.** The "Top Rated"/"4+ Stars" filter depended on `restaurants.avg_rating`, a column never present in any tracked migration (and possibly not on the live table at all). Removed the dependency entirely — ratings are now computed client-side from the `reviews` table (`restaurant_id, rating` where `status = 'approved'`), the same source the restaurant detail screen already used successfully.
- **Scanner — reports silently discarded.** "Report this result" inserted into `scan_reports`, a table referenced only in a migration *comment*, never actually created. The insert failed inside a silent catch, while the UI still showed "Thank you!" regardless. Added `supabase/migrations/015_scan_reports.sql` — written idempotently (per-column `ADD COLUMN IF NOT EXISTS`, not a single `CREATE TABLE`) after discovering the table already existed live with a different, incomplete shape (missing `status`) when the migration was first run.

No functional issues were found in Qibla or the restaurant detail screen.
